# CWE-787: Out-of-Bounds Write

**Category**: Memory Safety
**Severity**: Critical

Writing data outside allocated memory bounds can corrupt adjacent data, crash
the program, or allow arbitrary code execution.

## The Problem

Out-of-bounds writes occur when code writes to memory locations outside the
intended buffer. In memory-unsafe languages this enables buffer overflow
attacks. In Go, the `unsafe` package bypasses the runtime's bounds checking,
reintroducing this class of vulnerability.

## Defense

**Stay within the safe subset of the language. Avoid `unsafe` unless absolutely
necessary, and never with user-controlled sizes or offsets.**

### Go

```go
// WRONG: unsafe pointer arithmetic with user-controlled offset
func writeAt(buf []byte, offset int, value byte) {
    ptr := unsafe.Pointer(&buf[0])
    target := unsafe.Pointer(uintptr(ptr) + uintptr(offset))
    *(*byte)(target) = value // no bounds check
}

// RIGHT: let the runtime enforce bounds
func writeAt(buf []byte, offset int, value byte) error {
    if offset < 0 || offset >= len(buf) {
        return fmt.Errorf("offset %d out of range [0, %d)", offset, len(buf))
    }
    buf[offset] = value // runtime bounds check as safety net
    return nil
}
```

```go
// WRONG: unsafe.Slice with user-controlled length
data := unsafe.Slice((*byte)(ptr), userLength) // can read/write out of bounds

// RIGHT: if unsafe is truly required, validate all sizes against known allocations
if userLength > allocatedSize {
    return nil, errors.New("length exceeds allocation")
}
data := unsafe.Slice((*byte)(ptr), userLength)
```

```go
// WRONG: cgo with unchecked buffer sizes
C.memcpy(dst, src, C.size_t(userSize))

// RIGHT: validate size against both source and destination
if userSize > len(srcBuf) || userSize > len(dstBuf) {
    return errors.New("size exceeds buffer capacity")
}
C.memcpy(unsafe.Pointer(&dstBuf[0]), unsafe.Pointer(&srcBuf[0]), C.size_t(userSize))
```

## Key Rules

- Avoid the `unsafe` package; safe Go code cannot have out-of-bounds writes
- When `unsafe` is necessary (cgo, performance-critical code), validate all
  sizes and offsets against known allocation bounds
- Never use user-controlled values as lengths, offsets, or sizes in `unsafe`
  operations
- Run the race detector (`go test -race`); data races can cause out-of-bounds
  writes in concurrent code
- Review all cgo calls for buffer size mismatches between Go and C
