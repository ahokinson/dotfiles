# CWE-362: Race Conditions

**Category**: Concurrency
**Severity**: High

Concurrent access to shared state without synchronization leads to inconsistent
data, security bypasses, or privilege escalation.

## The Problem

When multiple threads, goroutines, or async tasks read and modify shared state
without proper synchronization, the outcome depends on execution order.
Attackers exploit this for double-spending, TOCTOU
(time-of-check-to-time-of-use) bypasses, and privilege escalation.

## Defense

**Eliminate shared mutable state, or protect it with appropriate
synchronization.**

### Go

```go
// WRONG: unsynchronized shared state
var balance int64

func withdraw(amount int64) error {
    if balance >= amount { // check
        balance -= amount  // act — race between check and act
        return nil
    }
    return errors.New("insufficient funds")
}

// RIGHT: mutex around check-and-act
var (
    balance int64
    mu      sync.Mutex
)

func withdraw(amount int64) error {
    mu.Lock()
    defer mu.Unlock()
    if balance >= amount {
        balance -= amount
        return nil
    }
    return errors.New("insufficient funds")
}
```

Use `go test -race` on every test run; it detects data races at runtime.

### Python

```python
# WRONG: async TOCTOU — await between check and act
async def withdraw(user_id: str, amount: int) -> None:
    balance = await get_balance(user_id)
    if balance >= amount:
        await set_balance(user_id, balance - amount)  # another coroutine may have changed it

# RIGHT: use database-level atomicity
async def withdraw(user_id: str, amount: int) -> None:
    result = await db.execute(
        "UPDATE accounts SET balance = balance - $1 "
        "WHERE user_id = $2 AND balance >= $1 "
        "RETURNING balance",
        amount, user_id,
    )
    if not result:
        raise InsufficientFundsError()
```

Python's GIL prevents data races in pure Python threads, but async/await code
has race conditions between `await` points. Database-level races exist
regardless of language.

### TypeScript

```typescript
// WRONG: read-modify-write without atomicity
async function withdraw(userId: string, amount: number): Promise<void> {
  const balance = await db.getBalance(userId)
  if (balance >= amount) {
    await db.setBalance(userId, balance - amount) // race window
  }
}

// RIGHT: atomic database operation
async function withdraw(userId: string, amount: number): Promise<void> {
  const result = await db.query(
    `UPDATE accounts SET balance = balance - $1
     WHERE user_id = $2 AND balance >= $1
     RETURNING balance`,
    [amount, userId],
  )
  if (result.rowCount === 0) throw new InsufficientFundsError()
}
```

Node.js is single-threaded, so in-memory races don't occur between synchronous
operations. But any `await` is a yield point; database-level and async races are
real.

## Key Rules

- Protect check-and-act sequences with locks, atomic operations, or database
  transactions
- Go: always run `go test -race`; use `sync.Mutex` or channels for shared state
- Python: use database atomicity for shared persistent state; use `asyncio.Lock`
  for shared in-memory state across coroutines
- TypeScript/Node: use database-level atomicity (`UPDATE ... WHERE`,
  transactions, `SELECT ... FOR UPDATE`)
- Prefer immutable data and message passing over shared mutable state
- For file operations: use `O_EXCL` / `O_CREATE` flags, advisory locks, or
  atomic rename patterns to prevent TOCTOU
